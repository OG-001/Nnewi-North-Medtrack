# Database: PostgreSQL schema, queries, and migrations

## Read this first

**There is no `apps/api/` and no PostgreSQL schema yet.** `infra/docker-compose.yml` starts
PostgreSQL 16 with database `phc_track` and development credentials `phc` / `phc_dev_only`,
waiting for Phase 1. No migration tool has been chosen; choosing one is a decision for the
owner, not a default you pick silently.

This database will hold the clinical records of real patients in Nnewi North LGA. Treat
every change to it as production-risk from the first migration onward.

Step 5 matters more than it looks. The client already persists these entities in IndexedDB.
A server schema that disagrees with `apps/web/src/db/types.ts` will fail at the first sync
push, and it will fail on a real device holding real unsynced work.

## Hard rules

- **No hard deletes of clinical data.** Every entity carries `deleted_at`. `DELETE FROM`,
  `DROP TABLE`, and `TRUNCATE` are blocked by the safety gate outside migration paths, and
  even inside one they need an explicit reason.
- **Every synced row carries the common columns**: `id`, `facility_id`, `created_at`,
  `created_by`, `updated_at`, `updated_by`, `rev`, `deleted_at`, `origin_device_id`.
- **`id` is a client-supplied UUID.** Never a database default, never a sequence, for any
  entity that can be created offline.
- **`facility_id` is on every clinical row and it is indexed.** It is the column the entire
  isolation model turns on.
- **Parameterised queries only.** String-concatenated SQL is a critical injection finding.
- **Server-side scope enforcement is enforced in the data layer**, not only in a guard. A
  query helper that can return another facility's rows is a defect even if every current
  caller passes the right scope.

## Migration safety checklist

Run this before **any** destructive migration, meaning one containing a drop, a new
`NOT NULL` on an existing column, a type change, or a rename.

1. Does this run against a database holding real patient data? If yes, **present the plan
   for owner acceptance before executing.** This is a production-risk operation.
2. Is there a data-migration step, or does the schema change silently drop data?
3. Do `up` and `down` both apply cleanly? Test both.
4. Is the table large enough that the lock will block clinic traffic?
5. Has a backup been taken, and has a restore been rehearsed?
6. Does the client's Dexie schema need a matching change? If yes, coordinate with
   `offline-sync` before either side ships.

Never run a downgrade against shared or real data without explicit owner confirmation for
that exact command.

## Write the migration body deliberately

An autogenerated diff is a starting point, not the answer. Read every statement it produced
and ask what it does to existing rows. Autogenerate is particularly unsafe here because it
cannot know that a column holds clinical data that must be preserved rather than recreated.

## Working with the running database

```bash
docker compose -f infra/docker-compose.yml up -d postgres
docker exec -it $(docker compose -f infra/docker-compose.yml ps -q postgres) \
  psql -U phc -d phc_track
```

Read-only inspection is fine. Any statement that writes, alters, or drops needs owner
approval for that exact statement.

## Output

Report: files changed, the schema delta in plain terms, the migration checklist answered
item by item, what you ran and what it printed, and any coordination `offline-sync` must do.
If you did not execute a migration because it needs owner approval, say so and present the
plan.

## Rules

- Never hard-delete clinical data.
- Never a server-generated identifier for a synced entity.
- Never a clinical table without an indexed `facility_id`.
- Never string-concatenate SQL.
- Never run a destructive migration against real data without explicit approval.
- Never trust an autogenerated migration body unread.
- Never choose the migration tool unilaterally. Present the options.
