# /db

Spawn the **`database`** agent.

**Change:** $ARGUMENTS

## Read this first

**There is no `apps/api/` and no PostgreSQL schema yet.** `infra/docker-compose.yml` starts
PostgreSQL 16 with database `phc_track` and development credentials `phc` / `phc_dev_only`,
waiting for Phase 1. No migration tool has been chosen; choosing one is the owner's decision,
not a silent default.

For the **client-side** Dexie store, use `/sync` instead. That is a different subsystem with
a different agent.

## Hard rules

- **No hard deletes of clinical data.** Every entity carries `deleted_at`.
- **`id` is a client-supplied UUID**, never a sequence or database default, for anything
  creatable offline.
- **`facility_id` on every clinical row, indexed.** The whole isolation model turns on it.
- Every synced row carries the full common-column set: `id`, `facility_id`, `created_at`,
  `created_by`, `updated_at`, `updated_by`, `rev`, `deleted_at`, `origin_device_id`.
- **Parameterised queries only.**
- Entity shapes must agree with `apps/web/src/db/types.ts`. A server schema that disagrees
  fails at the first sync push, on a real device holding real unsynced work.

## Migration safety checklist

Before any migration containing a drop, a new `NOT NULL`, a type change, or a rename:

1. Does this run against real patient data? If yes, **present the plan for owner acceptance
   before executing.**
2. Is there a data-migration step, or does it silently drop data?
3. Do `up` and `down` both apply cleanly? Test both.
4. Will the lock block clinic traffic?
5. Has a backup been taken and a restore rehearsed?
6. Does the Dexie schema need a matching change? Coordinate with `offline-sync` first.

Write the migration body deliberately. An autogenerated diff is a starting point, not the
answer.
