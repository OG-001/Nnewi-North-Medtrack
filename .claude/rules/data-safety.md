# Data safety: the local store, the repository layer, and PostgreSQL

**Applies to:** `apps/web/src/db/**`, `packages/shared/src/**` where it defines domain
shapes, and every future `apps/api/src/**` database path plus its migrations.

**Authority:** `docs/architecture/data-model.md` and
`docs/architecture/offline-sync-design.md`.

---

## 1. Hard rules

- **No hard deletes of clinical data** (Global Constraint 3). A delete sets `deleted_at` and
  writes an audit event. `DELETE FROM`, `DROP TABLE`, and `TRUNCATE` are blocked by
  [`../hooks/safety-gate.sh`](../hooks/safety-gate.sh) outside `infra/` and migration paths.
- **All local writes go through `apps/web/src/db/repository.ts`** (Global Constraint 4). One
  IndexedDB transaction writes the row, the outbox entry, the `rev` bump, and the audit
  event. Never call a Dexie table mutator from a component, page, or hook.
- **Client-generated UUIDs** for every synced entity, from `packages/shared/src/ids.ts`
  (Global Constraint 6). Never a server auto-increment, never a database default.
- **Every row carries the common columns**: `id`, `facility_id`, `created_at`, `created_by`,
  `updated_at`, `updated_by`, `rev`, `deleted_at`, `origin_device_id`. `createRecord` in the
  repository layer populates them; do not construct a domain row by hand.
- **Every read filters by scope and excludes soft-deleted rows**, through `useScope()` in
  `apps/web/src/lib/scope.ts` or the `notDeleted` helper beside it.
- **Parameterised queries only.** No string-concatenated SQL, ever.
- **Validate before persisting.** Zod on the client, and the same shape on the server, so an
  offline write cannot smuggle in a value the hub would reject.

## 2. The Dexie schema

Defined in `apps/web/src/db/db.ts`, typed in `apps/web/src/db/types.ts`, seeded in
`apps/web/src/db/seed.ts`. The table-to-entity mapping is the `ENTITY_TYPE_BY_TABLE` record
in `apps/web/src/db/repository.ts`; it currently covers:

`facilities`, `users`, `patients`, `patientLinks`, `encounters`, `referrals`, `pregnancies`,
`ancScheduleItems`, `ancVisits`, `deliveries`, `immunizationDoses`, `queueEntries`,
`smsMessages`, `monthlyReports`.

**Adding a table means four coordinated edits**, and missing any one produces a row that
never syncs:

1. The Dexie store definition and its version bump in `apps/web/src/db/db.ts`.
2. The TypeScript type in `apps/web/src/db/types.ts`, extending `BaseRecord`.
3. An entry in `ENTITY_TYPE_BY_TABLE` in `apps/web/src/db/repository.ts`.
4. Seed coverage in `apps/web/src/db/seed.ts` if the demo facilities need it.

**A Dexie version bump is a migration.** Existing installs carry real local data, and a
schema change that drops a store loses whatever had not synced. Treat it with the same care
as a PostgreSQL migration: state the upgrade path, and never remove a store in the same
change that adds its replacement.

## 3. PostgreSQL and migrations (Phase 1 onward, not built yet)

There is no `apps/api/` and therefore no migration tool chosen. When Phase 1 creates it:

- Schema changes go through a versioned migration. Never alter a table by hand.
- Write the migration body deliberately. An autogenerated diff is a starting point, not the
  answer.
- Both `up` and `down` must apply cleanly, and both must be tested.
- The hub must enforce facility scope server-side. That is the third isolation layer and the
  actual production guarantee.

### Migration safety checklist

Run this before **any** destructive migration, meaning one containing a drop, a new
`NOT NULL` on an existing column, a type change, or a rename.

1. Does this run against a database holding real patient data? If yes, **present the plan
   for owner acceptance before executing.**
2. Is there a data-migration step, or does the schema change silently drop data?
3. Do `up` and `down` both apply cleanly? Test both.
4. Is the table large enough that the lock will block clinic traffic?
5. Has a backup been taken and a restore rehearsed?

Never run a downgrade against shared or production data without explicit owner confirmation
for that exact command.

## 4. Reporting reads

`apps/web/src/lib/reporting.ts` aggregates local rows into NHMIS-shaped monthly summaries.
Two rules:

- Reporting reads **aggregates**, matching the purpose-limitation principle. A report must
  never carry an identifiable patient row into an export.
- A locked monthly report is immutable. Re-generating one is a new revision with an audit
  event, never an in-place overwrite.

---

## 5. Review checklist for any data-layer change

- [ ] Does every write path go through the repository layer?
- [ ] Is the outbox entry appended in the same transaction as the row?
- [ ] Is `rev` bumped and `updated_at` set?
- [ ] Is an audit event written?
- [ ] Are soft deletes used, with `deleted_at`, and never a hard delete?
- [ ] Does a new table appear in all four places listed in section 2?
- [ ] Is a Dexie version bump accompanied by a stated upgrade path for existing installs?
- [ ] Are reads scope-filtered and soft-delete-filtered?
